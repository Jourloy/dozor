# Подписанные выпуски и восстановление

## Сборка

Единственный источник номера версии — корневой файл `VERSION` в формате `vX.Y.Z`. Он встраивается в Go-бинарник при любой сборке, включая `make build` и `go run`, и копируется в пакет. Менять номер в команде сборки не нужно. Проверка: `./bin/dozor version`.

CI `.github/workflows/release.yml` запускается тегом `vX.Y.Z`, на Linux ARM64 в Debian bookworm. Тег должен точно совпадать с `VERSION`, иначе workflow завершается до сборки. В пакет входят `bin/dozor`, `bin/mediamtx`, `bin/ffmpeg`, `bin/ffprobe`, `VERSION`, `LICENSES/`. Основной бинарник Go использует CGO SQLite; сборка под macOS не является ARM64 Linux-выпуском.

Скрипт `scripts/build-release.sh` фиксирует SHA-256 официального архива MediaMTX 1.21.1 и исходников FFmpeg 8.0.1. FFmpeg собирается без внешних автоматически обнаруженных библиотек, документации и ffplay. Для записи H.264/AAC перекодирование не нужно; encoder libx264 требуется только тестовому генератору видеопотока.

Зависимости сборочного Linux ARM64-хоста: Go из `go.mod`, C/C++ compiler, make, pkg-config, curl, tar, xz, Python 3. Пример Debian:

```sh
sudo apt-get install -y ca-certificates curl git build-essential pkg-config xz-utils python3
bash scripts/build-release.sh
```

Артефакты — `dist/dozor_<VERSION>_linux_arm64.tar.gz` и исходный архив FFmpeg. Если передан необязательный аргумент, скрипт трактует его как ожидаемый тег и проверяет совпадение с `VERSION`; переопределить версию им нельзя. Перед упаковкой скрипт также проверяет вывод `bin/dozor version`. Сохраняйте исходники выпуска Dozor, сборочные флаги и license-файлы вместе с распространением бинарников. CI включает license-файлы Go-зависимостей и MediaMTX/FFmpeg; лицензию самого нового проекта владелец ещё должен выбрать перед публичной публикацией.

## Ключ и публикация

На доверенной машине владельца:

```sh
go run ./cmd/dozor keygen /secure/path/dozor-signing.key
```

Файл приватного ключа — base64 Ed25519, mode 0600; публичный — тот же путь с `.pub`. Приватный ключ не нужен на Raspberry. Для GitHub Actions добавьте его содержимое в secret `DOZOR_SIGNING_KEY`. Загрузку в GitHub/создание репозитория выполните отдельно; локальная реализация сама ничего не публикует.

На устройстве установите доверенный публичный ключ:

```sh
sudo install -o root -g root -m 0644 dozor-signing.key.pub /etc/dozor/update.pub
```

Адрес в настройках по умолчанию (также подставляется вместо пустого адреса в старых конфигурациях):

```text
https://github.com/Jourloy/dozor/releases/latest/download/release.json
```

Для такого GitHub-адреса обновлятор получает `tag_name` [последнего опубликованного стабильного релиза](https://docs.github.com/en/rest/releases/releases#get-the-latest-release), затем скачивает `release.json` именно этого тега. Обычный Git-тег без опубликованного пакета обновлением не является. Черновики и prerelease не устанавливаются. Версия в подписанных данных должна точно совпадать с тегом. Для другого HTTPS-сервера по-прежнему можно указать прямой адрес подписанного `release.json`.

Стабильный канал принимает только `vX.Y.Z`, без prerelease. CI подписывает канонический JSON структуры `release` (version/platform/url/sha256/size) и сохраняет подпись отдельно в `release.json`. Хеш покрывает весь tar.gz, включая видеокомпоненты. Для нового выпуска повысьте `VERSION`, зафиксируйте изменения и отправьте совпадающий тег; CI соберёт, подпишет и опубликует пакет. Номер существующего релиза повторно не используйте.

Для ручной подписи собранного пакета:

```sh
dozor_version=$(cat VERSION)
go run ./cmd/dozor sign \
  --key /secure/path/dozor-signing.key \
  --bundle "dist/dozor_${dozor_version}_linux_arm64.tar.gz" \
  --url "https://github.com/Jourloy/dozor/releases/download/${dozor_version}/dozor_${dozor_version}_linux_arm64.tar.gz" \
  --out dist/release.json
```

Команда подписи также использует встроенную версию проекта; старый флаг `--version` допускается только при совпадении с ней.

Initial install принимает уже распакованный доверенный каталог. Встроенная проверка подписи применяется к автоматическим последующим выпускам; установщик не выдаёт недоверенный первоначальный пакет за проверенный.

## Протокол установки

В **Настройки → Обновления** кнопка **Проверить и обновить сейчас** запускает ту же системную службу, даже если автообновление выключено. Используется сохранённый адрес выпуска. Новая версия устанавливается сразу после скачивания и проверок, с краткой остановкой записи; интерфейс показывает ход операции и результат. После перезапуска приложения потребуется войти снова. Политика polkit разрешает пользователю `dozor` только запуск этой службы; она обновляется вместе с приложением.

1. Ежедневный timer запускает независимый `/usr/local/libexec/dozor-system system update`. Версия берётся из сохранённого подписанного `current/.release.json`; для старых установок используются `/health` или ограниченный по времени `dozor version`. Маркер ручного запроса читается с диска. Ошибка конфигурации камер не мешает загрузке исправления: обновлятор читает только свои настройки и сохраняет их последнюю корректную копию в `/opt/dozor/updater-settings.json`.
2. Проверяются Ed25519, платформа, версия, подписанный размер (до 512 MiB) и SHA-256. Распаковка отклоняет выход из каталога, ссылки, лишние файлы, дубликаты и чрезмерные размеры. Проверенный пакет и подписанное описание сохраняются рядом с выпуском.
3. До остановки записи проверяется запуск и версия приложения. Неисправность видеобинарников диагностируется отдельно и не блокирует принятие выпуска. Новый кандидат дополнительно выполняет `system verify-update`: читает ключ, проверяет сохранённый пакет и пробует подготовить выпуск своим кодом в отдельном временном каталоге. Этот тест не обращается к сети.
4. Доступное приложение согласует окно обновления через `/prepare-update`. Ручной запрос отменяет сборку и восстановление; автоматический ждёт окончания активной записи. При недоступном или зависшем API проверенный пакет устанавливается после ограниченной по времени остановки службы systemd. Установка защищена межпроцессным `flock`.
5. Независимый `dozor-recover` сохраняется из запущенного системного помощника. Снимок включает прежний helper, polkit и `dozor-update.service`, их права и SHA-256. После fsync журнала служба останавливается, `current` переключается атомарно, системные файлы заменяются, выполняется daemon-reload и запускается кандидат.
6. `/health` сохраняет поля `version` и `ready`. Критичны публичный HTTP API, конфигурация/служебное состояние, короткая транзакция записи–фиксации–чтения активной SQLite и исправность команды/ключа/systemd-интеграции обновления. Полный архив не проверяется. MediaMTX, камеры, восстановление и отсутствующий архивный диск имеют отдельные состояния; неисправность видеосервиса не вызывает откат. Пропадание интернета после проверки пакета не мешает принять выпуск.
7. При успехе журнал и снимок удаляются. При критической ошибке возвращаются прежняя ссылка и системные файлы; сохраняется конкретная причина отказа health. Boot recovery выполняет те же действия после сбоя питания. Снимок имеет протокол 2; чтение протокола 1 (helper и polkit) сохранено.

Рабочий помощник обновляется из подписанного `bin/dozor`. Правила polkit экспортируются командой `system integration`; новые выпуски дополнительно сообщают `updater_protocol: 1`. Отдельных неподписанных загрузок нет. Mount/udev-файлы выбранного диска и пользовательская конфигурация не заменяются. Старые каталоги выпусков сохраняются: при ручной очистке оставляйте current, предыдущий выпуск и версии, упомянутые в pending journal.

## Переход с прежней установки

При переходе с v1.0.5 старый обновлятор ожидает `/health` не более 60 секунд. Новый процесс открывает рабочую SQLite и отвечает независимо от объёма архива; сверка старого формата идёт в фоне. После завершения установки приложение создаёт `update-reconcile-request` и через разрешённый systemd unit однократно запускает согласование helper, polkit и updater unit. Для установки, выполненной старым обновлятором без `.release.json`, согласование сохраняет root-owned `.confirmed-version`. Повторная установка пакета не требуется. Само согласование выполняется без сети.

После этого остановленное приложение не блокирует ежедневное обновление. Для ручного запуска из терминала используется `sudo systemctl start dozor-update.service`. Публичный ключ `/etc/dozor/update.pub` и доступный HTTPS-источник по-прежнему необходимы для скачивания новых выпусков.

Маркер перехода каталога фиксируется после окончания фоновой сверки и подтверждения установки. Установщик сохраняет новый идентификатор перехода `.catalog-transition`, если прежний выпуск не поддерживал журнал; старый установщик определяется по его восстановительной копии. Повторный запуск продолжает тот же переход, а установка после отката назначает сверку заново: изменения, сделанные старым приложением после отката, не теряются.

## Проверки выпуска

Перед тегом: `make test`, `make check`, `make integration`, установка на целевой ARM64-образ, обновление предыдущего выпуска, откат после неверного health и сбой питания в каждой фазе. Unit-тесты подписей/повреждений/пути распаковки/rollback дают программную проверку, но не заменяют испытание systemd и физического питания на Raspberry.
