# Подписанные выпуски и восстановление

## Сборка

Единственный источник номера версии — корневой файл `VERSION` в формате `vX.Y.Z`. Он встраивается в Go-бинарник при любой сборке, включая `make build` и `go run`, и копируется в пакет. Менять номер в команде сборки не нужно. Проверка: `./bin/dozor version`.

CI `.github/workflows/release.yml` запускается тегом `vX.Y.Z`, на Linux ARM64 в Debian bookworm. Тег должен точно совпадать с `VERSION`, иначе workflow завершается до сборки. В пакет входят `bin/dozor`, `bin/mediamtx`, `bin/ffmpeg`, `bin/ffprobe`, `VERSION`, `LICENSES/`. Основной бинарник Go использует CGO SQLite; сборка под macOS не является ARM64 Linux-выпуском.

Скрипт `scripts/build-release.sh` фиксирует SHA-256 официального архива MediaMTX 1.21.1 и исходников FFmpeg 8.0.1. FFmpeg собирается без внешних автоматически обнаруженных библиотек, документации и ffplay. Для записи H.264/AAC перекодирование не нужно; encoder libx264 требуется только тестовому генератору видеопотока.

Зависимости сборочного Linux ARM64-хоста: Go из `go.mod`, C/C++ compiler, make, pkg-config, curl, tar, xz, Python 3. Пример Debian:

```sh
sudo apt-get install -y ca-certificates curl git build-essential pkg-config xz-utils python3
bash scripts/build-release.sh
```

Артефакты — `dist/dozor_<VERSION>_linux_arm64.tar.gz` и исходный архив FFmpeg. Если передан необязательный аргумент, скрипт трактует его как ожидаемый тег и проверяет совпадение с `VERSION`; переопределить версию им нельзя. Перед упаковкой скрипт также проверяет вывод `bin/dozor version`. Сохраняйте исходники выпуска Dozor, сборочные флаги и license-файлы вместе с распространением бинарников. CI включает license-файлы Go-зависимостей и MediaMTX/FFmpeg; лицензию самого нового проекта владелец ещё должен выбрать перед публичной публикацией.

## Ключ и публикация

На доверенной машине владельца:

```sh
go run ./cmd/dozor keygen /secure/path/dozor-signing.key
```

Файл приватного ключа — base64 Ed25519, mode 0600; публичный — тот же путь с `.pub`. Приватный ключ не нужен на Raspberry. Для GitHub Actions добавьте его содержимое в secret `DOZOR_SIGNING_KEY`. Загрузку в GitHub/создание репозитория выполните отдельно; локальная реализация сама ничего не публикует.

На устройстве установите доверенный публичный ключ:

```sh
sudo install -o root -g root -m 0644 dozor-signing.key.pub /etc/dozor/update.pub
```

Адрес в настройках по умолчанию (также подставляется вместо пустого адреса в старых конфигурациях):

```text
https://github.com/Jourloy/dozor/releases/latest/download/release.json
```

Для такого GitHub-адреса обновлятор получает `tag_name` [последнего опубликованного стабильного релиза](https://docs.github.com/en/rest/releases/releases#get-the-latest-release), затем скачивает `release.json` именно этого тега. Обычный Git-тег без опубликованного пакета обновлением не является. Черновики и prerelease не устанавливаются. Версия в подписанных данных должна точно совпадать с тегом. Для другого HTTPS-сервера по-прежнему можно указать прямой адрес подписанного `release.json`.

Стабильный канал принимает только `vX.Y.Z`, без prerelease. CI подписывает канонический JSON структуры `release` (version/platform/url/sha256/size) и сохраняет подпись отдельно в `release.json`. Хеш покрывает весь tar.gz, включая видеокомпоненты. Для нового выпуска повысьте `VERSION`, зафиксируйте изменения и отправьте совпадающий тег; CI соберёт, подпишет и опубликует пакет. Номер существующего релиза повторно не используйте.

Для ручной подписи собранного пакета:

```sh
dozor_version=$(cat VERSION)
go run ./cmd/dozor sign \
  --key /secure/path/dozor-signing.key \
  --bundle "dist/dozor_${dozor_version}_linux_arm64.tar.gz" \
  --url "https://github.com/Jourloy/dozor/releases/download/${dozor_version}/dozor_${dozor_version}_linux_arm64.tar.gz" \
  --out dist/release.json
```

Команда подписи также использует встроенную версию проекта; старый флаг `--version` допускается только при совпадении с ней.

Initial install принимает уже распакованный доверенный каталог. Встроенная проверка подписи применяется к автоматическим последующим выпускам; установщик не выдаёт недоверенный первоначальный пакет за проверенный.

## Протокол установки

1. Ежедневный systemd timer с jitter до часа получает версию **работающего процесса** через закрытый Unix API `/health`, проверяет актуальный тег/HTTPS metadata и Ed25519. Если подписанная версия численно выше запущенной, начинается обновление; равные и более старые версии пропускаются. Файл `/opt/dozor/current/VERSION` не участвует в сравнении. Если процесс недоступен, обновление откладывается. Ключ хранится root-owned отдельно от доступной приложению конфигурации.
2. Скачивание ограничено подписанным размером (до 512 MiB), проверяется SHA-256. Распаковка отклоняет выход из каталога, ссылки, лишние файлы, дубликаты и чрезмерные размеры.
3. Все четыре бинарника проверяются запуском `version`/`--version`/`-version` ещё до остановки работающей версии. Вывод `dozor version` должен совпасть с подписанной версией. После скачивания версия работающего процесса проверяется ещё раз, чтобы не устанавливать устаревший пакет, если приложение уже обновилось.
4. Запрос приватному control socket резервирует окно без движения/незакрытых событий. Если событие активно, пакет остаётся подготовленным, установка повторится при следующей проверке; вручную можно запустить timer service после события.
5. fsync-журнал фиксирует предыдущую версию; служба останавливается, ссылка `current` переключается через rename, служба запускается.
6. За 60 секунд проверяется версия, открытие каталога либо нормальная работа без выбранного HDD, а при доступном архиве — запуск MediaMTX. Камера/интернет могут быть недоступны и сами по себе не требуют отката приложения.
7. При успехе журнал удаляется. При неудаче восстанавливается прежняя ссылка и запускается старая служба. После отключения питания boot recovery читает тот же журнал до запуска приложения.

Служба обновления запускает `/opt/dozor/current/bin/dozor system update`, поэтому новая версия приложения приносит и новую логику обновления. Стабильный `/usr/local/libexec/dozor-system` установлен отдельно от `current` и используется для восстановления и выбора диска, чтобы повреждённый кандидат не ломал откат. Этот системный помощник и systemd/polkit/udev integration не заменяются автоматически пакетом приложения: несовместимое изменение протокола восстановления или системных units требует отдельного обслуживания установщика. Старые каталоги версий сохраняются; удалять их можно вручную после проверки, оставляя current/предыдущий выпуск и любые версии из pending journal.

`systemd` запускает updater единственным unit; не запускайте второй ручной экземпляр привилегированного helper одновременно. ОС, загрузчик, прошивки EZVIZ и схемы базы с несовместимой миграцией этим механизмом не обновляются.

## Переход с прежней установки

На уже установленной Raspberry Pi один раз обновите unit из свежих исходников, чтобы следующие обновления использовали текущую программу вместо копии первого выпуска:

```sh
sudo install -o root -g root -m 0644 ops/dozor-update.service /etc/systemd/system/dozor-update.service
sudo systemctl daemon-reload
sudo systemctl enable --now dozor-update.timer
```

В настройках включите автообновление и проверьте адрес `https://github.com/Jourloy/dozor/releases/latest/download/release.json` (до первого перехода старая программа сама его не подставляет). Установите публичный ключ `/etc/dozor/update.pub`, соответствующий `DOZOR_SIGNING_KEY` выпуска. После публикации нового подписанного релиза можно сразу выполнить `sudo systemctl start dozor-update.service`; дальше проверка выполняется ежедневно. Изменения исходников на компьютере разработчика сами по себе не меняют установленную программу или unit на Raspberry.

## Проверки выпуска

Перед тегом: `make test`, `make check`, `make integration`, установка на целевой ARM64-образ, обновление предыдущего выпуска, откат после неверного health и сбой питания в каждой фазе. Unit-тесты подписей/повреждений/пути распаковки/rollback дают программную проверку, но не заменяют испытание systemd и физического питания на Raspberry.
