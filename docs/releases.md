# Подписанные выпуски и восстановление

## Сборка

CI `.github/workflows/release.yml` запускается тегом `vX.Y.Z`, на Linux ARM64 в Debian bookworm. В пакет входят `bin/dozor`, `bin/mediamtx`, `bin/ffmpeg`, `bin/ffprobe`, `VERSION`, `LICENSES/`. Основной бинарник Go использует CGO SQLite; сборка под macOS не является ARM64 Linux-выпуском.

Скрипт `scripts/build-release.sh v0.1.0` фиксирует SHA-256 официального архива MediaMTX 1.21.1 и исходников FFmpeg 8.0.1. FFmpeg собирается без внешних автоматически обнаруженных библиотек, документации и ffplay. Для записи H.264/AAC перекодирование не нужно; encoder libx264 требуется только тестовому генератору видеопотока.

Зависимости сборочного Linux ARM64-хоста: Go из `go.mod`, C/C++ compiler, make, pkg-config, curl, tar, xz, Python 3. Пример Debian:

```sh
sudo apt-get install -y ca-certificates curl git build-essential pkg-config xz-utils python3
bash scripts/build-release.sh v0.1.0
```

Артефакты — `dist/dozor_v0.1.0_linux_arm64.tar.gz` и исходный архив FFmpeg. Сохраняйте исходники выпуска Dozor, сборочные флаги и license-файлы вместе с распространением бинарников. CI включает license-файлы Go-зависимостей и MediaMTX/FFmpeg; лицензию самого нового проекта владелец ещё должен выбрать перед публичной публикацией.

## Ключ и публикация

На доверенной машине владельца:

```sh
go run ./cmd/dozor keygen /secure/path/dozor-signing.key
```

Файл приватного ключа — base64 Ed25519, mode 0600; публичный — тот же путь с `.pub`. Приватный ключ не нужен на Raspberry. Для GitHub Actions добавьте его содержимое в secret `DOZOR_SIGNING_KEY`. Загрузку в GitHub/создание репозитория выполните отдельно; локальная реализация сама ничего не публикует.

На устройстве установите доверенный публичный ключ:

```sh
sudo install -o root -g root -m 0644 dozor-signing.key.pub /etc/dozor/update.pub
```

Адрес в настройках:

```text
https://github.com/OWNER/REPO/releases/latest/download/release.json
```

Стабильный канал принимает только `vX.Y.Z`, без prerelease. CI подписывает канонический JSON структуры `release` (version/platform/url/sha256/size) и сохраняет подпись отдельно в `release.json`. Хеш покрывает весь tar.gz, включая видеокомпоненты.

Для ручной подписи собранного пакета:

```sh
go run ./cmd/dozor sign \
  --key /secure/path/dozor-signing.key \
  --bundle dist/dozor_v0.1.0_linux_arm64.tar.gz \
  --version v0.1.0 \
  --url https://github.com/OWNER/REPO/releases/download/v0.1.0/dozor_v0.1.0_linux_arm64.tar.gz \
  --out dist/release.json
```

Initial install принимает уже распакованный доверенный каталог. Встроенная проверка подписи применяется к автоматическим последующим выпускам; установщик не выдаёт недоверенный первоначальный пакет за проверенный.

## Протокол установки

1. Ежедневный systemd timer с jitter до часа проверяет HTTPS metadata и Ed25519. Ключ хранится root-owned отдельно от доступной приложению конфигурации.
2. Скачивание ограничено подписанным размером (до 512 MiB), проверяется SHA-256. Распаковка отклоняет выход из каталога, ссылки, лишние файлы, дубликаты и чрезмерные размеры.
3. Все четыре бинарника проверяются запуском `version`/`--version`/`-version` ещё до остановки работающей версии.
4. Запрос приватному control socket резервирует окно без движения/незакрытых событий. Если событие активно, пакет остаётся подготовленным, установка повторится при следующей проверке; вручную можно запустить timer service после события.
5. fsync-журнал фиксирует предыдущую версию; служба останавливается, ссылка `current` переключается через rename, служба запускается.
6. За 60 секунд проверяется версия, открытие каталога либо нормальная работа без выбранного HDD, а при доступном архиве — запуск MediaMTX. Камера/интернет могут быть недоступны и сами по себе не требуют отката приложения.
7. При успехе журнал удаляется. При неудаче восстанавливается прежняя ссылка и запускается старая служба. После отключения питания boot recovery читает тот же журнал до запуска приложения.

Стабильный `/usr/local/libexec/dozor-system` установлен отдельно от `current`, чтобы повреждённый кандидат не ломал механизм восстановления. Этот небольшой системный помощник и systemd/polkit/udev integration не заменяются автоматически пакетом приложения: несовместимое изменение протокола updater или системных units требует отдельного обслуживания установщика. Старые каталоги версий сохраняются; удалять их можно вручную после проверки, оставляя current/предыдущий выпуск и любые версии из pending journal.

`systemd` запускает updater единственным unit; не запускайте второй ручной экземпляр привилегированного helper одновременно. ОС, загрузчик, прошивки EZVIZ и схемы базы с несовместимой миграцией этим механизмом не обновляются.

## Проверки выпуска

Перед тегом: `make test`, `make check`, `make integration`, установка на целевой ARM64-образ, обновление предыдущего выпуска, откат после неверного health и сбой питания в каждой фазе. Unit-тесты подписей/повреждений/пути распаковки/rollback дают программную проверку, но не заменяют испытание systemd и физического питания на Raspberry.
