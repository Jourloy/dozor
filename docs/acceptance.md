# Проверки и аппаратная приёмка

## Что проверено при разработке

На macOS ARM64, Go 1.26.1, установленном FFmpeg 9.0.1 и MediaMTX 1.21.1:

- Unit/integration Go с race detector: окна события и повторное движение, ошибки детектора, маски/прогрев, очистка с приоритетом S3 и учётом потери, восстановление каталога/очереди, guard, скрытие секретов, первый вход и CSRF.
- Реальный FFmpeg remux и чтение результата ffprobe.
- Тестовый S3 HTTP endpoint: работа AWS SDK, PUT/HEAD, контрольные суммы, стабильный ключ, повтор после ошибки и завершение manifest.
- HTTPS-пакеты с Ed25519: неверная подпись, подмена metadata, недопустимые пути tar, откат при плохом health и восстановление pending journal.
- Браузер: вход, сохранение настроек/отключённой камеры, открытие каталога и воспроизведение H.264-файла; адаптация к экрану 390 px.
- `TestRTSPPipeline`: настоящий RTSP/TCP через MediaMTX, 72 секунды спокойной сцены, движение, предыстория, две воспроизводимые MP4-части и S3/manifest с проверкой MD5/SHA-256 на HTTP endpoint. Последний прогон: PASS, 115 секунд. Запускается отдельно через `make integration`.

Тестовые сервисы не подтверждают совместимость с настоящей EZVIZ, AWS или сторонним S3-провайдером. Фактические результаты очередного запуска сохраняйте вместе с commit/tag и версиями бинарников. Linux ARM64 release workflow подготовлен, но выполнение GitHub Actions и установка Linux-пакета не могут быть подтверждены локальной macOS-проверкой.

## Обязательные проверки на Raspberry Pi

| Проверка | Действие | Ожидаемый результат |
|---|---|---|
| Одна настоящая камера | Добавить основной H.264 и малый поток, создать движение | Доступные 60 секунд до, всё движение, 10 после; готовая часть играет и скачивается |
| Повторные срабатывания | Движение, пауза 9 секунд, движение; затем пауза >10 | Первая пара продлевает событие, вторая создаёт новое |
| Неполная предыстория | Движение сразу после запуска | Событие доступно, отмечена неполная предыстория |
| Длительное движение | 30–60 минут движения | Части появляются примерно раз в минуту и отправляются до окончания события |
| Ночь/свет/маска | ИК-режим, включение света, движение в маске | Настроена чувствительность; маска подавляет локальный детектор; известны ложные срабатывания |
| ONVIF | Подписка, событие, unsubscribe, неверный пароль | Камера действительно сообщает движение; при непроверенном ONVIF auto переходит на local |
| Отказ детектора | Отключить малый поток при доступном основном | Видимая ошибка и резервный непрерывный архив; после восстановления обычный режим |
| Камера пропала | Отключить её сеть и вернуть | Переподключение; разрыв заметен в статусе и интервалах, без выдуманного покрытия |
| Интернет пропал | Отключить WAN на несколько часов | Локальные события продолжаются; очередь переживает перезапуск и догружается |
| HDD отключён/возвращён | На тестовых данных отсоединить USB и вернуть тот же диск | Запись остановилась; в пустом `/srv/dozor` на microSD файлов нет; тот же UUID снова монтируется |
| Диск заполнен | Заполнить **тестовый** раздел, S3 недоступен | При 90% очистка до 85%; сначала uploaded; потеря unuploaded отражена; новые события записываются |
| Активное длинное событие | Заполнение диска во время записи | Старые закрытые части не удерживаются бесконечно |
| Перезапуск/power loss | Прервать remux/публикацию/загрузку | Незавершённое не опубликовано; очередь восстановлена; стабильные cloud keys |
| S3 AWS + совместимый сервер | PUT/HEAD, потеря ответа PUT, рестарт, сверка скачанного SHA-256 | Один логический key каждой части, правильный manifest; облачное удаление не выполняется |
| Ошибочное обновление | Неверная подпись/хеш, неработающий кандидат | Работающий выпуск сохраняется либо автоматически возвращается |
| Питание при update | Прервать download/stage/switch/health на тестовом устройстве | Загрузка устройства и восстановление предыдущего выпуска из journal |

Для проверки питания и заполнения используйте тестовый архив. Записывайте точное время действий, чтобы сверять события и сообщения.

## 72-часовой прогон четырёх камер

1. Зафиксируйте модель каждой камеры, прошивку, основной/малый кодек и битрейт, GOP, источник движения, параметры масок, HDD/USB-питание, Pi OS/kernel и версию Dozor.
2. Запустите четыре камеры одновременно, S3 и просмотр в браузере. Организуйте реальные/воспроизводимые движения и спокойные промежутки. Проверяйте ночью и днём.
3. Собирайте статус:

   ```sh
   python3 scripts/soak.py http://raspberrypi.local:8080 --hours 72 --cameras 4 --out soak-72h.csv
   ```

   Пароль вводится интерактивно. Скрипт только читает API, переживает истечение сессии, не меняет настройки и не перезаписывает имеющийся CSV. Ненулевой код завершения обозначает замеры с проблемой, а не автоматический диагноз. Включённые в испытание плановые отключения тоже попадут в них.
4. На Raspberry параллельно контролируйте CPU/RSS, swap, температуру/throttling, I/O, свободное место и журнал `journalctl -u dozor`. CSV не измеряет нагрузку процессора и не доказывает отсутствие потерянных кадров.
5. Сопоставьте известные движения с фактическими границами MP4/пропусками, скачайте выборку облачных объектов и сравните SHA-256. После восстановления WAN очередь должна убывать при достаточной исходящей скорости.
6. Зафиксируйте сбои, число удалённых до отправки частей и восстановление после каждого воздействия. Приёмка пройдена только после анализа видео/облака/метрик, а не потому что процесс прожил 72 часа.

Модели EZVIZ, настоящий HDD/Pi и облачные credentials ещё не предоставлены. Поэтому перечисленные аппаратные сценарии и 72-часовой результат остаются открытыми.
