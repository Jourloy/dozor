# Устройство Dozor

## Модули

| Файл | Ответственность |
|---|---|
| `cmd/dozor/main.go` | CLI, HTTP-сервер, остановка дочерних процессов, ключи/подпись |
| `config.go`, `http.go` | настройки, редактирование камер, авторизация, API |
| `app.go` | жизненный цикл HDD, MediaMTX, детекторов и uploader |
| `media.go` | ffprobe, конфигурация MediaMTX, регистрация фрагментов, remux |
| `live.go` | прокси HLS на loopback, проверка камеры и состояния видеослужбы |
| `motion.go`, `onvif.go` | `MotionSource`, adaptive background, WS-Discovery, SOAP/WSSE/Digest, PullPoint |
| `engine.go` | состояния движения, окна событий, части, завершение |
| `availability.go` | состояние основного потока, история доступности за 24 часа, завершение записи при отключении |
| `store.go` | SQLite, файлы-описания, сверка, буфер и очистка |
| `upload.go` | S3 SDK, лимит скорости, durable queue, контрольные суммы |
| `disk.go`, `system.go` | UUID/ext4/exFAT guard и привилегированные системные операции |
| `update.go` | проверка подписи, распаковка, переключение и rollback journal |
| `system_update.go`, `ops/embed.go` | обновление рабочего помощника и polkit, независимое восстановление системных файлов |
| `web/` | встроенный интерфейс: HTML, CSS, классические `app.js` и `live.js`, локальные hls.js, шрифты и иконки; без CDN и сборки. Решения — в [ui.md](ui.md) |

## Основные инварианты

1. Без проверенного HDD работает только управление. Видео/SQLite никогда не переключаются на microSD.
2. MediaMTX пишет в буфер, а не непосредственно в публичный каталог событий. Хук закрытия отправляет путь/длительность через Unix socket 0600; периодическая сверка компенсирует пропущенный хук.
3. `Event.Start/End` — запрошенное окно; `Part.Start/End` — фактические границы фрагментов. Все значения времени — Unix milliseconds UTC. `Part.Gaps` и `Event.Incomplete` сохраняют пропуски.
4. Буфер старше 75 секунд удаляется, только если не нужен несобранному событию. Уже собранные закрытые MP4-части независимы от буфера.
5. Публикация MP4: remux во временный файл → ffprobe → SHA-256/MD5 → fsync → описание → rename → каталог → задание. Recovery завершает проверенный rename и восстанавливает пропущенные шаги. Недописанные части пересобираются из закреплённого буфера.
6. SQLite использует WAL, synchronous=FULL и одну открытую связь. `Event`, `RecordingPart` (Go `Part`), `UploadJob` имеют стабильные идентификаторы. Очередь дедуплицируется по `kind:ref`.
7. Из локального каталога удаляются только готовые видеофайлы. Сначала записывается tombstone; cloud-флаг и потеря сохраняются в истории. Активный Event не запрещает удалять его старые закрытые части.
8. Облако не является зеркалом удаления. Event полностью выгружен, только если нет потерянных частей и подтверждены все PUT/HEAD, включая описание.
9. Обновление скачивается и проверяется до остановки записи. При активном событии установка откладывается до следующей проверки. Между резервированием окна и остановкой возможен короткий перерыв записи; это не бесшовное обновление.

Mount namespace службы допускает появление/исчезновение монтирований с хоста; дополнительный guard проверяет присутствие устройства и UUID, а не только запись в mount table. Такое распространение монтирований описано в [документации systemd](https://github.com/systemd/systemd/blob/main/man/systemd.exec.xml). Реальный hotplug всё равно проверяется на целевой ОС.

После подключения диска поверх служебного bind mount таблица может содержать несколько записей с одним путём. Guard использует `findmnt --uniq`, чтобы проверять видимый раздел, исключая перекрытые слои ([документация util-linux](https://manpages.debian.org/bookworm/util-linux/findmnt.8.en.html)). Проверки UUID, файловой системы и режима записи при этом сохраняются.

Настройки камеры/S3 сейчас перезапускают видеослужбы, чтобы применить конфигурацию согласованно. Во время такого применения возможен разрыв; начатое событие после перезапуска помечается как прерванное. Для базовой версии выбран простой последовательный жизненный цикл; изменения отдельных камер без общего перезапуска можно сделать следующим этапом.

Ошибка сборки или проверки видео отдельного события не блокирует запуск видеослужб и обработку остальных событий. Неудачная часть остаётся в буфере для повторной обработки; сбой восстановления отмечается в журнале. Ошибки доступа к диску и каталогу по-прежнему останавливают запуск. При выбранном диске интерфейс различает запуск записи и недоступный архив и не предлагает выбрать диск заново.

## HTTP API `/api/v1`

JSON, UTF-8; ошибки имеют `{"error":"..."}`. Для доступа нужна cookie `dozor_session`; для POST/PUT/DELETE после входа — `X-CSRF-Token`, полученный из `/auth` или `/login`. CORS не включён. Секреты никогда не возвращаются; пустой пароль при изменении означает «оставить прежний».

| Метод и путь | Назначение |
|---|---|
| `GET /auth` | `authenticated`, `setup_required`, `csrf` |
| `POST /login` | `{password, token}`; token нужен только при первом запуске |
| `POST /logout` | завершение сессии |
| `GET /status` | состояние HDD, камер, детекторов, очередь, журнал, обновление |
| `GET /availability?camera=` | последние 24 часа: `{start, end, cameras: [{camera_id, name, intervals: [{start, end, state}]}]}`; `state`: `online`, `offline`, `disabled`; пробелы означают отсутствие наблюдений |
| `GET /settings` | конфигурация с удалёнными секретами, камеры |
| `PUT /settings` | `{timezone, s3, auto_update, release_url}` |
| `PUT /cameras/new` | создать камеру, проверить включённые потоки |
| `PUT /cameras/{id}` | изменить камеру; ID 32 hex |
| `DELETE /cameras/{id}` | удалить конфигурацию камеры, оставить архив |
| `GET /cameras/{id}/live/{file}` | HLS: `index.m3u8`, относительные плейлисты и MP4-фрагменты; GET/HEAD/Range, сессия проверяется на каждом запросе |
| `POST /cameras/probe` | Camera → кодеки/размер/совместимость браузера |
| `POST /discovery` | WS-Discovery, ~4 секунды |
| `POST /profiles` | Camera с ONVIF/credentials → RTSP-профили |
| `GET /events?camera=&date=YYYY-MM-DD&offset=0` | до 200 событий; дата в выбранной timezone; пересекающиеся с датой окна |
| `GET /events/{id}` | `{event, parts}` с удалёнными/потерянными частями |
| `GET /parts/{id}/video` | локальная MP4-часть; Range/HEAD; `?download=1` |
| `GET /disks` | дерево lsblk, текущий UUID, признак development |
| `POST /disks/select` | `{uuid}` → systemd helper; только существующий ext4 или exFAT |

Пример Camera (пароль передаётся отдельно от URL):

```json
{
  "name": "Двор",
  "url": "rtsp://192.168.1.50:554/main",
  "sub_url": "rtsp://192.168.1.50:554/sub",
  "username": "admin",
  "password": "CAMERA_PASSWORD",
  "onvif": "http://192.168.1.50/onvif/device_service",
  "motion": "auto",
  "sensitivity": 0.7,
  "masks": [],
  "enabled": true
}
```

API не исполняет произвольные команды, не форматирует диски, не устанавливает обновления от имени HTTP-пользователя. Настройка/статус обновлений входят в settings/status; привилегированная установка запускается ежедневным systemd timer. Закрытый Unix API содержит `/segment`, `/stream`, `/prepare-update`, `/health` и не публикуется по сети.

MediaMTX отправляет `runOnOnline` / `runOnOffline` через `dozor hook --stream online|offline`. Отключение прекращает продление события детектором, сверяет последний файл буфера и собирает все оставшиеся части на ближайшем тике. Поздний хук последнего фрагмента может дозавершить прерванное событие. `Event.DisconnectedAt` и `Part.DisconnectedAt` (`disconnected_at`, Unix milliseconds) обозначают последнее событие и ровно одну последнюю часть перед отключением; отметки входят в JSON-описания и S3-манифест. Уже выгруженный манифест ставится в очередь повторно.

`availability` в SQLite хранит наблюдавшиеся интервалы отдельно от 75-секундного видеобуфера. Граница текущего интервала обновляется каждую секунду; данные за пределами 24 часов удаляются, пересекающий границу интервал обрезается. Перезапуск оставляет неизвестный промежуток. При пропуске хуков свежий фрагмент подтверждает подключение, а отсутствие фрагментов в течение 20 секунд завершает запись как отключённую. Ошибка отдельного детектора при доступном основном потоке сохраняет прежний режим непрерывной записи.

HLS работает на `127.0.0.1:8888`, в формате fMP4, без перекодирования. Сегменты хранятся в RAM; remux включается только при просмотре и завершается через 15 секунд без запросов. Прокси допускает только известные включённые камеры и одиночные имена `.m3u8`/`.mp4`, не передаёт upstream cookie/Authorization и не выдаёт его ошибки, редиректы или CORS. Каждый запрос ограничен 30 секундами и не удерживает блокировку приложения. Ответы API имеют `Cache-Control: no-store`. Без диска либо запущенного MediaMTX возвращается 503, для отключённой камеры — 409, неизвестной — 404; недоступный поток — 502.

## Совместимость и границы

- ONVIF Media v1, PullPoint, WSSE PasswordDigest и HTTP Digest MD5/SHA-256. Нет обещания совместимости с каждой реализацией ONVIF: некоторые камеры используют иные темы, Media2, дополнительные EPR ReferenceParameters или vendor API. При непроверенном источнике auto использует локальный детектор.
- WS-Discovery — IPv4 multicast текущего маршрута; не сканер всех VLAN/интерфейсов.
- SQLite и конфигурация обновляются добавлением полей/таблиц без удаления старых в совместимых выпусках. Миграция, нарушающая чтение предыдущим выпуском, запрещена в автоматическом канале.
- В исходниках нет готового облачного аккаунта, приватных ключей выпуска или заданного GitHub owner. Их настраивает владелец развёртывания.
